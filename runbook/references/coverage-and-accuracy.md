# Case 覆盖与执行准确率

在执行准备前把测试目标映射为去重后的 Case（行为取决于多个状态维度组合的功能，例如 launch 门禁，按 [维度矩阵 Case 设计](case-matrix.md) 展开，每个格子都要有预期或登记缺口），执行中逐项更新；目标是所有计划内、当前适用的 Case 都有实际执行和可核验的结论，**不是用重复 Case 做大数字**。

## 规划和去重

- 候选 Case 按 [Case 设计：七个生成器](case-design.md) 逐个推导，每个生成器都要有结论（产出或不适用及理由），每个机制标 `generator`。下面的规则负责去重、预算和冻结。
- 对每个 checklist 项或 Goal 目标记录：权威 Expected、`applies_when`、角色/组织、业务终点、需要的 UI 与持久事实、覆盖它的 Case ID。再从相关权限、状态边界、异步/幂等、恢复及 [时序风险](temporal-risk-cases.md) 选择有不同失效机制的 edge case。
- 两个候选若角色、前置、操作路径、业务终点与核心断言相同，只留一个 Case，把附带断言并入；只有不同的前置、事件顺序、风险或需要独立隔离的数据/副作用能区分它们时才拆 Case。一条完整路径可覆盖多个 checklist 项。
- 普通 ticket 的两条风险 smoke 是默认成本预算，不是高风险功能的绝对上限；确有多个独立高代价失效机制时按范围补足，并在任务模型写明价值和额外成本。Goal/repeat 不按数量凑 Case。
- 冻结执行计划时为每条 Case 记录稳定 ID、目标映射、唯一风险、预期事实、数据/副作用和预期执行器；执行中发现新风险可追加并说明来源，不能静默删掉失败或难测项来提高分母。
- 初版计划的目标→独立机制→Case 映射在业务 UI 执行前按 [Case 漏测 Hook](omission-hook.md) 单独冻结；PR-only 还应从精确 base/head diff 构造 changed-file→changeId→目标映射。后续自查、真实执行或人类反馈指出漏项时另记发现与裁定，不能把补测后的 Case 回填初版分母。没有事前人类盲审时不计算设计召回率。
- 同一任务模型中给每个去重 Case 标一个主类型 `happy`、`negative` 或 `edge`，记录独立失效机制与预期出处；多个风险标签不重复计数。尚无权威预期或安全 fixture 的边界探索列候选池，不伪装成计划内 Case。逐轮与同旅程回归的比较口径见 [Loop Engineering Hook](loop-engineering-hooks.md)。

## 执行闭环

- 每个计划内且适用的 Case 必须从正确账号/组织与已知前置启动，走到业务终点或具体阻塞，保留逐 Case video 和关键事实。不能只点到中间页面便记 Pass。
- 前置实际不成立且该行为本来不适用，用 `NotApplicable` 并保留依据；本应可测但环境/权限/安全边界阻止动作，用 `Blocked`、恢复条件和已执行部分。先尝试已授权的替代数据/路径或轻量协作，不绕过安全边界；`Blocked`、`NotRun`、`Inconclusive` 不算已完成执行。
- 未执行的 Case 不能伪造视频或事实；在交付前对原计划与新增 Case 逐项核对状态。若计划内适用 Case 没有完整执行，要明确披露并给出续跑入口，整轮不能声称“100% 执行”或完整通过。
- 按三种主类型分别留去重设计数、实际适用数、达到业务终点的执行数和有足够证据的可判定数；Blocked、NotRun、NotApplicable 的原因单列。回归关注独立失效机制的覆盖增长，不能拿重复 Case 数替代执行能力。

## 正确判定

- Pass：身份、组织、目标 SHA、数据前置和 UI 动作真实成立；必要断言由持久/结构化事实核对，video 非空；每条所映射目标都有证据。Action 返回的 `visible: true` 或点击成功不是业务 Pass。
- 失败：冻结首次偏差和视频；记录环境/SHA、角色/组织、初始对象状态、输入、事件顺序、最小步骤、预期/实际、已排除的脚本/误点/环境原因与副作用状态。可安全复现时从已知初始状态独立重跑；高风险不能重做时如实写 `observed_once`，不能用刷新同一对象充当复现。
- 度量分别看适用目标的执行与明确结论覆盖、去重后计划内 Case 的完整执行率、首跑到业务终点率，以及失败 Case 中复现条件/证据完整率。报告分母固定为计划内适用目标和 Case，新增/剔除均留原因；不设“为了达标而凑 Case”的数量指标。
