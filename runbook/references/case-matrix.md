# 门禁类功能的维度矩阵 Case 设计

适用：功能的行为取决于几个**状态维度的组合**（例如「组织 tracker 状态 × campaign 类型 × 目标」决定一道 launch 门禁）。这类功能只照工单清单逐条测，会漏掉清单没写的组合；只测主路径，会漏掉门禁在某些组合下该拦没拦、不该拦却拦了。

## 1. 列维度

先从模块、工单和代码事实（只用来枚举取值，不定义 Expected）里找出**真正影响行为的维度**和取值。例：转化追踪门禁（`QA-models/hellyeah/campaign-composer.md`「测试矩阵：转化追踪门禁」）

- tracker 状态：未安装 / 已安装未首访（waiting）/ 已收到访问（live）
- campaign 类型：Search / PMax
- 目标：只按是否需要 tracker 分组（Sales、Signups 需要；Leads 只提示；Traffic 不需要），每组取一个代表即可

不影响行为的维度不展开。

## 2. 列观察点

每个格子都看同一组观察点，每个观察点都要有预期：

1. 门禁提示是否出现（卡片、阻塞行、文案）
2. launch 是否被拦：UI（Launch Readiness、Launch 按钮）**和**服务端（调 launch 接口，被拒时不扣钱，可以安全探测）
3. 处理按钮是否出现（例如切换按钮）
4. 点按钮之后发生什么（弹窗内容、确认后的类型 / 目标 / 出价、能否回退）

## 3. 每个格子都要有预期

- 预期来自 QA 模块断言、工单明确声明或用户确认；**代码只能用来列取值，不能定义预期**。
- 没有预期的格子**不能悄悄跳过**：在工作台登记 C 类知识候选（写清是哪个格子、哪个观察点、可选的预期），本轮在报告「未覆盖」里列出。
- 格子太多时可以合并，但要写出理由：例如两个目标在门禁上行为一致，就只测一个代表。合并不能把「拦」和「不拦」两类格子并成一类。

## 4. 与工单、风险 smoke 的关系

- 工单清单圈定这一轮碰了哪个功能；矩阵决定这个功能该验哪些组合。矩阵格子属于这一轮的**主 Case**，不受「风险 smoke 最多两条」的限制。
- 优先级：先覆盖每个「状态 × 类型」组合至少一次（门禁拦不拦最容易出错），再补按钮点击后的行为。
- 数据：共享 fixture 只能用一次、不能动的，就自己新建带 runId 的对象（例如新建 PMax / Search 草稿），或者用 disposable 账号；确实造不出来的格子记 `Blocked` 并写恢复条件。

## 5. 报告

报告的覆盖统计里附矩阵：每个格子的结论（Pass / ProductFail / Blocked / 无预期已登记），让读者一眼看出哪些组合被验证过。
